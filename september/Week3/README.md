# September Week 3 — LLM APIs & Prompt Engineering

## Objective

Learn how to integrate an LLM into a Python application using an API and understand the fundamentals of prompt engineering, structured output, tokens, temperature, rate limits, and LLM evaluation.

---

## Topics Covered

### 1. LLM APIs

Learned how a Python application can communicate with an LLM through an API.

Basic architecture:

Python Application → LLM API → LLM → Response → Python Application

The SDK handles the underlying API communication so the application can focus on the business logic.

---

### 2. API Keys & Environment Variables

Learned why API keys should not be hard-coded into source code.

The Gemini API key was stored as an environment variable:

```powershell
$env:GEMINI_API_KEY="YOUR_API_KEY"

Python accesses it through the environment.
This prevents the API key from being directly stored in the source code.
3. Prompt Engineering
Learned to structure prompts using:
- Role
- Context
- Task
- Constraints
- Output Format
Example:
Role → Project Risk Analyst

Context → Project information

Task → Determine project risk

Constraints → Follow defined business rules

Output → Structured risk assessment

4. Business Rules and LLMs
Learned that business rules should be explicitly defined when predictable behavior is required.
For the project risk analyzer:
A project is delayed if delay_days > 0.

High Risk:
cost > ₹10 lakh AND delay_days > 0

Medium Risk:
delay_days > 0 AND cost <= ₹10 lakh

Low Risk:
delay_days = 0

5. Structured Output
Instead of asking the LLM to return free-form text, structured output was used.
The expected structure was defined using Pydantic models.
Example:
class RiskAssessment(BaseModel):
    project_name: str
    risk_level: RiskLevel
    reason: str
    recommended_actions: list[str]

This makes the LLM response easier for Python applications to process reliably.
6. Pydantic Validation
Pydantic was used to validate the structured response returned by the LLM.
The response was converted into a Python object:
risk = RiskAssessment.model_validate_json(
    interaction.output_text
)

This provides a validation layer between the LLM response and the application.
7. Tokens
Learned that LLM usage involves tokens.
Two important concepts:
- Input tokens — information sent to the model
- Output tokens — information generated by the model
Token usage and API request count are separate concepts.
For example:
1 API request
+
Many tokens
is still one API request.
8. Temperature
Learned that temperature influences how varied or deterministic model responses can be.
General principle:
- Lower temperature → more predictable output
- Higher temperature → more variation and creativity
For business analysis tasks where consistency is important, lower variability is generally preferable.
9. Rate Limits
Learned that LLM APIs have usage limits.
Important concepts include:
- Requests per minute
- Requests per day
- Tokens per minute
An application can therefore fail even when the Python code itself is correct.
During this project, a Gemini Free Tier request limit was reached and produced a 429 TooManyRequests error.
10. LLM Evaluation
Learned that an LLM application should be evaluated against expected results rather than simply assuming the response is correct.
The project used deterministic business rules to calculate the expected risk level.
The AI result was then compared with the expected result.
Accuracy:
Correct predictions / Total predictions × 100

Build a Python application that retrieves project data from SQLite, sends multiple projects to an LLM, receives structured risk assessments, and evaluates the AI results against deterministic business rules.

Important Data Quality Learning
During evaluation, an inconsistency was identified in the Mobile App data.
The database contained:
Status: On Track
Delay: 10 days
Initially, using the status field to determine whether the project was delayed would have classified this differently.
The business rule was therefore clarified to use:
delay_days > 0
as the definition of a delayed project.
This demonstrates an important Business Analysis principle:
AI evaluation is only meaningful when the underlying data and business rules are clearly defined.

Key Learnings
1. Python can orchestrate an LLM through an API.
2. API keys should be kept outside source code.
3. Prompt structure significantly affects the usefulness of LLM responses.
4. Business rules should be explicit when predictable classification is required.
5. Structured output makes LLM responses easier for applications to consume.
6. Pydantic can validate LLM-generated JSON.
7. API request limits and token usage are different concepts.
8. LLM applications need evaluation against expected results.
9. Data quality and business-rule clarity are important before evaluating AI.
10. Multiple pieces of information can be processed in a single LLM request.
